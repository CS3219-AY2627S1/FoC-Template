# CHANGE-171 — Courier-submitted Order reports

Date: 2026-11-01. Owner: Yao Xiang, hfix/report-service. AI assistance: OpenAI Codex; human review pending.
Status: implemented and verified locally with the user's ERRAND category amendment; human review/cloud rollout pending.

## Approved amendment

User decision: "new type called errand ... allow the courier to choose the order they works and go to admin straight." Implement ERRAND for the currently assigned courier, ORDER for the actual requester, GENERAL unlinked. ERRAND starts READY_FOR_REVIEW with no self-response/deadline/reminder. Existing hold, one-active-report and resolution/compensation rules remain. This supersedes the proposal's category-neutral courier submission and pending response-routing decision below.

Concrete compatible contract extension: GET /api/orders/mine/active accepts optional mode=requester|courier, default requester. The existing hold body gains optional reporterRole=REQUESTER|COURIER, default REQUESTER; required requireAssignedCourier remains. Report sets the role from its category, never from browser-submitted participant IDs. SQL scopes list/lock to that role and authenticated subject, and verified role checks do not use current courier eligibility as permission to report an existing assignment. New Report requesterId stores actual owner separately from reporterId; legacy documents fall back to reporterId. Hold rows remain bound to the actual requester, so no SQL migration or compensation schema/topic change is needed. Admin and form labels identify submitter/category correctly. No requester-response workflow is added.

## Request and current evidence

The user requests allowing a courier to report their assigned order, in addition to the existing requester submission. Current PDF fingerprints match the recorded baseline; effective developer identity and branch match. Root, Order, frontend instructions, mandated context, existing contracts and actual Report/Order implementations were inspected. Existing report-hold and resolution amendments govern the funding/saga behavior.

Existing implementation: GET /api/orders/mine/active and PUT /api/orders/mine/active/{orderId}/report-holds/{reportId} restrict ownership to requester_id in SQL and require requester role. ReportService checks reporterId=requesterId; every linked report starts a response request for courierId. ReportResolutionStore also compares the coordinator's requesterId against reporterId. Merely allowing courier ownership would therefore create a self-response prompt and break resolution binding. Admin UI labels the submitter as Requester. Existing reports store reporterId and courierId without a separate actual requesterId.

Expected contract extension: the same Order list/hold routes accept a verified requester or currently assigned courier whose token subject matches the scoped Order. Existing statuses remain ACCEPTED, IN_PROGRESS, PICKED_UP and DELIVERED; OPEN, terminal and unrelated orders remain excluded. SQL filters ownership/status before paging, and placement uses a locked transaction. Classification: expectation-changing contract amendment; approval of the detailed response behavior is requested before coding.

## Proposed design

- Keep reporterId as the authenticated submitter. Add actual requesterId to new linked Report documents and responses, populated from the authoritative hold response. Existing documents fall back to reporterId, preserving their historical requester-submitted meaning; GENERAL remains unlinked. No SQL schema change or history rewrite is planned.
- Keep Order hold binding to the real order requester, regardless of who submits. Validate the caller as a participant before any hold mutation. Preserve current-snapshot idempotent retries, report-ID binding, released-ID fencing, pending-command guards, locking and one-active-report-per-order.
- Proposal A (recommended): requester submissions retain the existing courier response/deadline workflow; courier submissions start READY_FOR_REVIEW, without a response deadline, self-response reminder or self-entry under Reports against me. They appear under Reports I submitted. Admin handles them using existing review actions. This does not add a requester-response workflow.
- Alternative B: request a response from the requester. This requires a generic respondent identity/type, response fields/API/authorization, two-sided notification/list behavior and revised deadlines. It provides a response opportunity for both parties but materially broadens the feature. Await the user's decision; do not silently implement it.
- Report resolution validates actual requesterId/courierId, independently of reporterId. Existing synchronous resolve then local hold release, durable compensation, generation fencing, stable event/command IDs and inbox/outbox semantics stay unchanged. No new topic or cross-service call is proposed. Historical reports and saved resolutions retain their bindings.
- Keep admin replies private to the submitter and admin. Clearly label the Report submitter separately from the Order requester/courier in admin details. The courier's own submitted case does not solicit a courier response. Existing requester-report access and response behavior remain.
- Reuse the existing form/dropdown, actual Order API, shared components, exact Order navigation and five-second polling. Copy explains that an order can be reported by its requester or assigned courier. No new report category, penalty policy, report-resolution business action or sibling backend change.

## Sequence and boundaries

Authenticated browser -> SQL-scoped participant Order list -> multipart Report submission -> authenticated locked Order validation/hold -> Report document with actual participants and submitter -> existing admin review -> existing Order-coordinated resolution/compensation. Delivery may progress while held; ordinary funding and penalty outcomes remain paused. Report placement does not publish a penalty or modify credits. Changing who may submit does not resolve the pre-existing hold-created/Report-save-failed recovery gap.

No broker choice changes: immediate ownership/hold validation and resolution remain synchronous because they need authoritative outcomes. Polling discovers reports. The existing durable broker compensation remains only for cross-service recovery; an in-process signal cannot replace its crash recovery. Duplicate/order/failure/security behavior remains the existing approved saga's responsibility.
