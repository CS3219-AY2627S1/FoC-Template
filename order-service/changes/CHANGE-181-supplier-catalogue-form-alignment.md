## Supplier selection redesign proposal - awaiting approval

The user asks for a design that does not fetch/display an arbitrarily large catalogue. The all-pages fix above restores today's missing options only; it is not a large-scale design and would be replaced by the approved search design. No search-index/backend/schema provision or redesigned selector is implemented under this proposal.

1. Replace each pickup/delivery Select with the existing design system's accessible searchable combobox. Show a search hint when empty, require2 trimmed characters and debounce300ms. Query at most20 active suppliers; show name/building/floor and a distinct selected value. Retain stable Supplier ID as the order payload and keep pickup/delivery IDs different. Never download all pages or put the full catalogue in a browser cache.
2. Initial compatible API: authenticated GET /api/suppliers?status=active&q=Vincent&page=1&size=20&sort=name&order=asc. Existing service searches name/building/location description. Load the next matching page only on explicit Show more; changing search resets its page. Abort old searches and check request identity so late results cannot replace newer results. Keep selected records visible after the search text/results change. Distinct loading, no-match, authentication, unavailable and retry states; keyboard/touch and320px layout verification. No raw HTML from service text, no new browser authentication scheme or direct database access.
3. Critical backend limit: SupplierService.catalogue() calls repository.findAll() and CatalogueSearch filters/sorts the full catalogue in memory. Browser filtering/paging alone cannot scale that implementation to100million suppliers. This requires a separately approved Supplier-owned indexed search/query path. Prefix search could use normalized indexed name/building fields; full substring/multi-field search requires a suitable indexed search capability. Choose actual database edition/index product and consistency contract with the Supplier owner before changing its storage.
4. At large scale use bounded cursor pagination instead of deep page offsets/exact total-count scans. A proposed additive search contract could return {items:[{id,name,building,floor}],nextCursor}; cursor bound to query/filters/order, deterministic name+ID tie-break, server-limited page size and rejection of invalid cursors. No unbounded blank query. Only show20 results per response, using virtualization only if the accumulated visible result list warrants it.
5. Keep Supplier Service authoritative: search results are suggestions, not reservations. Existing Order-side Supplier pair validation rechecks actual existence/active status at submission. An inactive/deleted result can be rejected clearly and refreshed. If an external index is chosen, define synchronization and deletion lag rather than claiming immediate search visibility.
6. Delivery stages: first approve/implement the bounded searchable UI using the existing API for the campus catalogue; separately approve backend indexed search and cursors for genuinely large datasets. Tests cover debounce and minimum input, exact/partial name, duplicate names with different buildings, later-page selection, aborted/out-of-order replies, no matches, retries, stale/inactive selected IDs, same pickup/delivery rejection and keyboard/mobile behavior. No claim that100million-record load testing has been performed.

Primary reference: Firestore cursor pagination, https://firebase.google.com/docs/firestore/query-data/query-cursors. This supports bounded page retrieval; it does not make the current in-memory search scalable by itself.
